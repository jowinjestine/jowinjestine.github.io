The workload and the box

Arjay's Twelve-Dollar Server Challenge runs competing implementations of the same small feed API on the same unmodified VPS: one Xeon Platinum 8260 virtual CPU, 2 GB of RAM, no swap, and a fresh SQLite seed database for each run. Clients request feeds, create posts, and sometimes like them. Each implementation must pass a 42-check correctness suite before the load test; the published score is the number of virtual users it can hold for five minutes while keeping p95 below 500 ms, p99 below one second, and errors below 1%.

The hard limit was not simply throughput. With so little memory, every accepted connection consumes part of the budget. With one CPU, a slow database checkpoint or an unexpectedly long event-loop pass can delay thousands of other requests at once. At high concurrency, packet processing and delayed acknowledgements can become just as relevant as application code.

How the implementation is structured

The implementation uses C and Linux io_uring to manage network work in batches, reads SQLite B-tree pages for hot-path lookups, and keeps checkpoint work from monopolizing the request loop. Two merged pull requests document the specific performance and memory changes I contributed.

Decision 1: bound the work of checkpointing

A write-ahead log lets SQLite commit without rewriting the whole database on each request. That defers work; it does not remove it. Earlier attempts could accumulate a large WAL and eventually force a costly catch-up on the same CPU that was supposed to answer requests.

In merged PR #404, I worked on making the checkpoint cycle converge to a small remaining tail, allowing a bounded write hold when restarting the WAL, and kicking off background writeback ahead of expensive syncs. This is a useful example of latency engineering: a long rare pause matters more to p99 than a small saving on the average request.

Trade-off / brief controlled holds and a bounded log, instead of allowing an occasional unbounded stall to determine the whole run.

Decision 2: treat TCP buffers as part of application memory

At hundreds of thousands of persistent connections, the kernel's per-socket allocation competes directly with the database and application for RAM. It is not enough to watch the process's resident memory.

Merged PR #486 added a pressure-aware TCP receive-memory governor. It samples cgroup v2 memory usage and pressure-stall information, plus kernel socket statistics. With hysteresis, it tightens the receive-buffer setting used for future accepted sockets during pressure and relaxes it after sustained recovery. Existing sockets are deliberately not rewritten by that merged design.

The official score associated with this implementation is 300,000 users and 28,394 requests per second. The result should not be described as proof that the governor alone caused every improvement: the score belongs to the full system.

What the next experiments are trying to resolve

Once the 300,000-user run passed, the remaining problem was a latency cliff. Higher load did not necessarily produce application errors; more often, the queue stopped draining quickly enough and p99 breached the scoring limit. I have used independent, switchable experiments to isolate causes rather than treating every new idea as an automatic improvement.

  • #538 — Event-loop phase tracing Open / diagnosticInstrument wait, ready-queue, database, CQ reaping, reads, commits and flushes to find which phase creates the long turns. The instrumentation is optional so the uninstrumented baseline remains comparable.
  • #521 — Live receive-buffer updates Open / experimentalTests updating receive-buffer settings on already accepted fixed-file sockets using temporary installed descriptors. The PR itself calls for correctness testing and benchmarking; no official performance gain is claimed here.
  • #540 — Deadline-aware, newest-first scheduling Open / local measurementsExplores answering recent arrivals before old backlog work, while guaranteeing the old backlog eventual service. Also investigates connection caps and a faster SQLite rowid lookup path. The linked PR documents multiple 320,000-user local test runs, but they are not official challenge scores.
Official vs. experimental results

The 300,000-user benchmark is published by the challenge organizer. Results attached to unmerged PRs use separate local machines, durations and conditions; they are engineering evidence, not interchangeable with the organizer's five-minute leaderboard score.

What I learned

There are no independent knobs at this scale. A shorter receive buffer saves memory but changes packet and receive behavior. A larger answer batch amortizes overhead but can make everyone else wait. Checkpointing less often saves work until it leaves a log too large to recover from. A scheduler that improves p95 may still fail the p99 requirement.

My approach has been to make changes reversible, compare against the same baseline, measure latency and kernel memory together, and leave the unsuccessful experiments visible. That is how a tiny server challenge becomes useful systems-engineering practice rather than a collection of benchmark tricks.
